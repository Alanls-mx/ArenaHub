# Protocolo da agenda em tempo real

Endpoint `GET /api/v1/orgs/:slug/agenda/stream` com upgrade WebSocket e cookie de sessão. O proxy do host ArenaHub deve encaminhar o upgrade à API. Origem e host são verificados na abertura; o canal é somente leitura e mensagens do cliente encerram a conexão (`1008`).

O servidor envia `{"type":"agenda.connected"}` na abertura e `{"type":"agenda.invalidate","kind":"reservation.changed"}` (ou `block.changed`, `recurrence.changed`, `recurrence.conflict`, `listener.reconnected`) após mudanças. O payload não inclui cliente, preço, token ou dados de outra organização. A mensagem é **invalidação**, não estado definitivo: o navegador refaz `GET /agenda` ao conectar, receber evento, ganhar foco ou quando o operador atualiza manualmente. Invalidações próximas são agrupadas por um segundo na Web; disponibilidade também é atualizada. A tela de contratos recarrega após mutações de recorrência.

`pg_notify` é executado na transação de domínio e só chega ao listener depois do commit. Cada processo API possui um `LISTEN` dedicado com reconexão; o worker publica na mesma transação PostgreSQL. O listener valida formato e tamanho da mensagem; cada assinante é revalidado antes do envio. Eventos ocorridos durante uma revalidação são coalescidos em uma invalidação pendente. Evento perdido não é reentregue; reconexão aciona refetch. Os testes cobrem entrega pós-commit, revogação de membership e sessão, payload de cliente indevido, atualização entre dois navegadores, recuperação da conexão `LISTEN` após encerramento pelo PostgreSQL e parada total do banco em container descartável com porta fixa. Nesse último teste, o WebSocket permaneceu aberto, recebeu `listener.reconnected` e uma nova invalidação após o retorno; a agenda HTTP voltou a responder. O primeiro fixture experimental usou porta dinâmica e mudou de endereço ao reiniciar o container; o ensaio válido usa porta fixa, sem alteração no código de produção.
